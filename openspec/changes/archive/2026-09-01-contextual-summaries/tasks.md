## 9. Review round

Two reviewers on the PR diff, one for correctness and one for security. They independently found the
same top defect, and between them found two blocking issues that each falsified a scenario this change
itself publishes. Recorded here rather than in the PR alone, because the defects are more instructive
than the fixes.

- [x] 9.1 **BLOCKING — `check()` was never called from any production path.** Both reviewers found it. `OpenAICompatSummariser.check()` was defined, documented as the control, named in the published requirement, and dead: the only `check()` call in `src/` was the reranker's. So an unreachable endpoint failed every document individually instead of being fatal for the run, falsifying `chunking-and-embedding`'s *An unreachable producer is fatal for the run* and `layered-configuration`'s *A summariser that cannot be reached is fatal*. The security reviewer ranked it higher, for the better reason: `check` is the one request in a run that carries no evidence, so without it the first thing a wrong endpoint receives is corpus text — once per chunk, for the whole casefile. Fixed by calling it at the start of `ingest()` beside the existing `self._router.gate.verify()`, which is the same control for the same reason one rung down. *Watched failing: with the call disabled the new test reports `DID NOT RAISE ConfigError`.*
- [x] 9.2 **BLOCKING — the document summary was written after the chunks were committed.** `_rebuild_chunks` wrote chunks and vectors and *then* computed the document summary, so a `summarise_document` failure reported the document as failed while its row, text and chunks were already stored and searchable — the exact state `chunking-and-embedding`'s new scenario says cannot exist. Reachable with `chunk_summaries: false`, the configuration this change documents as corpus-safe. Worse second-order effect, found by running it: a failed document is not expanded, so an archive whose summary failed was stored with its entries never ingested, `refusals` empty and `IngestReport.complete` still `True` — a silent partial ingest of an archive that was read successfully. Fixed by inverting the order: `_rebuild_chunks` became `_prepare_chunks`, which chunks, summarises and embeds while writing nothing, and the caller persists only once every fallible step has succeeded. *Watched failing: with the old ordering restored, the new test reports 3 rows and 3 chunks left behind.*
- [x] 9.3 **The related asymmetry the same fix closed.** `upsert_document` ran before `_rebuild_chunks`, so a chunk-summariser failure left a document row with zero chunks — listed and readable through every document surface while no search could return it, which makes an analyst's negative result over that casefile wrong. Every prior per-document failure left nothing behind, because `ValidationError` and `ExtractionError` both arise before the first write; this one now matches them.
- [x] 9.4 **The recipe guard covered four of five components.** `enable_thinking` was added to the hashed recipe earlier in this change and to neither test dict, so dropping it from `_RECIPE` left all 510 tests green — the guard that replaces a hand-bumped version number did not cover the newest and most likely-to-be-edited component. *Watched failing after the fix.*
- [x] 9.5 **The summary-to-chunk pairing was unguarded.** Reversing the zip in the fold left the entire suite green. The folding-on oracle reads `chunks.summary` back from the store, which is sound for the *transformation* and blind to the *pairing*, because a mispaired summary is what gets stored — both sides of the comparison move together. Closed with an assertion that recomputes the stub's output from the chunk it was given, an oracle outside the pipeline. This was the one unguarded path to precisely the failure class the whole change exists to prevent: vectors of the declared width, under a correct identity, meaning something else. *Watched failing with the zip reversed.*
- [x] 9.6 **A credential embedded in `llm_url` reached an unauthenticated REST response.** Error messages interpolated the composed endpoint URL, and a `SummaryError` becomes an `IngestOutcome.detail` which the REST ingest route returns in its body with no authentication in front of it. Several OpenAI-compatible gateways carry the credential as userinfo, a path token or a query parameter. Fixed with a `_redacted` helper — scheme, host, port and path only — used everywhere a message names the endpoint. *Watched failing: with the raw URL restored, the test finds the token in the message.*
- [x] 9.7 **`trust_env` was left at httpx's default.** `HTTPS_PROXY` in the ingesting process would have routed every summary request — up to 20,000 characters of a document each, plus the bearer token — through a host appearing nowhere in `config.yaml`. Set `trust_env=False`, and pinned `follow_redirects=False` and `verify=True` explicitly: both are correct defaults today, and `httpx>=0.28` does not stop a minor release flipping either. A 3xx would otherwise replay the Authorization header to whatever the Location header names. *Both watched failing.*
- [x] 9.8 **MCP was the only surface without a chunk summary, and nothing guarded that.** REST and the CLI carry `chunk.summary` on a hit; MCP deliberately does not.
