## 9. Review round

Two reviewers on the PR diff, correctness and security. Both confirmed the core claim — the predicate
really is inside the SQL of both legs, inside the vec `MATCH` subquery, with correct parameter ordering
and fully bound values, verified by running the store rather than reading it — and both found defects
the change had shipped anyway. Recorded here because the defects are more instructive than the fixes,
and because two of them falsify sentences this change itself published.

- [x] 9.1 **The caller's `--mention` value was never normalised.** The store holds `normalised`; the caller types what the document showed them, so the two sides of the comparison were produced by different rules. `Billing@Acme.example` → 0 passages, `billing@acme.example` → 1. Three of the four kinds affected; only `registration_number` normalises to itself. This is the silent empty result that reads as "this casefile does not mention that" — the precise failure the filter placement exists to prevent, arriving by a different route — and it contradicts the requirement published in this change: "The filter SHALL match the normalised form, so a caller pivots on an identifier regardless of how the document wrote it." **My own smoke test missed it because I pivoted on the value the facet returns, which is already normalised, rather than on the spelling a human would copy out of a passage.** Fixed by asking the extractors, so a fifth extractor is normalised correctly by existing; an extractor's answer is taken only when it recognises the whole value, since a partial match would search for something narrower than was asked. *Watched failing: 0 passages against 4.*
- [x] 9.2 **The unfenced facet payload rested on a false premise, and mine was the false premise.** The comment I wrote argued `listing_payload` needs no fence because "an identifier has no sentences for an instruction to hide in and is bounded by its own format". Both halves were false for the email kind, and the security reviewer built the counterexample end to end: the local part admits `.`, `_`, `%`, `+` and `-` as word separators with no length bound, so one match was a 1,417-character sentence, and the store held a 528-character one. Planted at chosen repetition counts — the ordering is by frequency, so the adversary chooses the line order too — legible directives came back through the real MCP server, in a payload the surface's own `INSTRUCTIONS` tell an agent to read *first*, with no notice, no fence and no provenance. Two things changed rather than one: the pattern is bounded at RFC 5321's limits, and the payload now carries `content_notice`, because a length bound is not an argument that nothing objectionable fits. What remains true, and is why values are not fenced individually, is that no facet value can forge a row — three kinds normalise to `[0-9+]` or `[A-Z0-9]` and the email charset admits no whitespace — and that a fenced value could not be passed back as a filter, which is the whole point of the inventory. *Watched failing both ways: unbounded, a value reached 1,683 characters; without the notice, the payload declares nothing.*
- [x] 9.3 **The email pattern backtracked quadratically.** The same RFC bound closed it. An unbounded greedy local part before a mandatory `@`, and an unbounded `(label\.)+` before a mandatory letters-only label, re-scan from every start position on text where neither ever satisfies: measured 4x per doubling, 21 ms for one 2,000-character chunk against 0.23 ms bounded, and 5.7 s per megabyte of crafted text against 0.05 s benign. A chunk is adversary-controlled and nothing gates extraction, so it was a free amplification for anyone who could get a document ingested — and it falsified the `mentions` spec's own "costs milliseconds", which is the stated reason there is no setting to switch extraction off. Now 0.20 ms at 2,000 chars and linear, with parity on real addresses. *Watched failing on the mutation that actually causes it — the unbounded local part, 13.8x for 4x input. Unbounding only the domain does not go quadratic, so the test staying green there is correct rather than a gap.*
- [x] 9.4 **`replace_chunks` trusted the mention's denormalised ids.** The foreign keys prove those ids exist somewhere, not that they agree with the chunk. The reviewer planted a mention whose `chunk_id` named one casefile and whose `casefile_id` named another; the write was accepted and the second casefile's inventory then advertised an identifier that existed only in the first's text. The retrievers were safe — both constrain the casefile twice — but the facet has no second constraint, and a casefile is the compartment. Now derived from the chunk being written, which makes it unreachable rather than merely unused. That matters because this registry is advertised as the seam a model-backed producer arrives through. *Watched failing.*
- [x] 9.5 **I found one the reviewers did not: chunk overlap inflated the mention count.** Chunks overlap by the contract's overlap, so an identifier near a boundary is extracted from two chunks of one document and `COUNT(*)` reported it twice — making the spec's own "how many times it was mentioned" wrong by exactly the overlap, and wrong invisibly, since nothing in the figure said which occurrences were the same one seen twice. Established by sweeping an identifier across a boundary until a duplicate appeared: one occurrence, two rows. Fixed with a `document_offset` column on the still-unreleased step 7 and `COUNT(DISTINCT document_id || ':' || document_offset)`, which is exact — one occurrence has one offset in its document however many chunks it lands in. *Watched failing: three rows for two occurrences counted as 3.*
- [x] 9.6 **A published scenario asserted something false and untestable.** "The passages present in both are ranked relative to each other identically, **and no score differs**" — false by construction, because filtering removes rows from each retriever's ordered output so survivors move up in rank, and RRF scores are computed from ranks. Measured: all four passages present in both runs have different scores. The change's own test says so and asserts the reciprocal-rank sum instead, so nothing in the suite could ever fail on that sentence — it would have sat in the published spec until someone read it as the contract and "fixed" the implementation to match. Corrected in both the published spec and the archived delta, so the two cannot disagree.
- [x] 9.7 Two smaller ones taken rather than argued: the casefile slug is now collapsed with `one_line` in the inventory header, matching every other line-oriented block in that file; and the Ukrainian phone vector carries a note saying it is synthetic, since it was the only identifier in the suite not traceable to a published reserved set — the IBAN is ISO 13616's own example and the addresses use RFC 2606's `.example`, but Ukraine publishes no reserved subscriber range.
- [x] 9.8 Re-run every gate after the fixes. *Six mutations applied against a throwaway copy of `src`, five red on the first pass and the sixth red once aimed at the mutation that actually causes the fault.*

**Accepted rather than fixed.** The IBAN extractor trims a candidate group by group until mod-97 holds,
and one prefix in 97 passes by chance, so an IBAN-shaped run of random alphanumerics matches about
0.45% of the time — measured over 4,000 synthetic runs. Real text contains very few strings shaped like
two letters, two digits and five groups of four, so the expected count over a corpus of this size is
well under one, and the alternative — refusing to trim — would reject any account printed with a word
after it. Worth knowing rather than worth changing, and the facet is an inventory of what was found in
any case.
